# Sync entrypoints

Use this workflow for an audit of a harness's global block, a Brain routing fix, a development build of the tool or a desktop handoff. The tool writes one managed block into each harness's global instructions file (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, under `CLAUDE_CONFIG_DIR` and `CODEX_HOME` when set) and nothing into a repository (ADR-0011). The block holds the invocation table, the never-fetch rule and the Brain section; its text is the tool's own (`src/block.ts` in oneezy/tools), so a change to it reaches machines with a tool release (ADR-0008), not with a library release. `skills-sync.entrypoints.json` and `assets/brain-routing.md` here feed only `adopt-brain`. Keep Brain account, locations and schema in `/oneezy-brain`.

1. Inspect current state: `status --json` gives each harness's `block` (`status`: `current`, `missing`, `outdated` or `conflict`) and `repoBlocks`, the blocks an older version left in repository files, which are reported and removed by hand. Check existing rollout branches in oneezy/tools. Preserve dirty work and pinned sources. For `adopt-brain`, `rollback-brain`, `migrate-aliases` and `rollback-aliases`, which verify a library checkout, pass the full `--expect-revision <sha>` and the exact `--remote-ref refs/heads/main` (or a verified release tag); the source must be clean and origin must still advertise that revision. `sync` and `status` take neither: they read the latest release.
2. Change the block text, the tool or the library templates in an isolated development checkout. Follow Justin's requested development/review scope; a desktop handoff or a request to avoid publication stops before the Land workflow.
3. Build and test the reviewed tool. Point `SKILLS_SYNC_CLI` at its built `dist/src/cli.js`; both platform scripts run that file through Node. For a published rollout, clear that variable and use the latest published tool. Run the script with `sync --plan --json` and finish this step only when every harness, block, hook entry and plugin action is accounted for.
4. Run the same script without `--plan`. The tool changes only the bytes between its markers, keeps every other byte and line ending, refuses a broken or doubled marker pair and a hook file it cannot edit, and reads its writes back. A conflict fails the run; resolve it before retrying. Record the exact tool and library commits and every resulting path.
5. Run the script with `status --json`. Done is `ok: true` and `manualSteps: []`; list any open step. Then start a fresh host session and verify that its loaded instructions route a Brain lookup through the current Drive registry. File readback alone does not prove automatic invocation or Drive connector access.

For a desktop handoff, supply the exact commits, build/test results, plan/apply/status commands and required host prerequisites. A coordinating task may dispatch them to an existing authorized desktop task. Report each inaccessible computer, WSL distro or connector as a blocker. A cloud test, prepared handoff or dispatch is not desktop execution.

For the four explicitly approved historical Brain links only, use the reviewed CLI's `adopt-brain --adoption-file <manifest> --receipt <durable-json>` through the canonical platform script, with the exact expected revision/ref. The version 1 manifest lists this host's literal `path` and `expectedTarget` pairs. Preview first. Adoption rechecks the expected target immediately before mutation, preserves the original link as a named backup, reads back the new target and propagates only verified Brain entrypoints. It does not run broad sync or unlink, install plugins, or alter other skills and projects. Repeat to prove idempotence. `rollback-brain --receipt <same-json>` restores only unchanged owned adopted links; later edits require reconciliation. Keep the reviewed library and receipts durable. A source checkout is not a released plugin.

The tool propagates the global files of Claude Code and Codex; Hermes has no global instructions file, so it has no block. `CODEX_HOME` and `CLAUDE_CONFIG_DIR` are respected. System policy, harness settings and additional configured instruction directories need separate host inspection. Keep old Spaces and pinned history intact.
